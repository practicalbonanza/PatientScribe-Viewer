# Contributing

**Contributions are not accepted.**

This repository is published for review, not for collaboration. Pull requests, patches and
feature requests are not accepted, and issues are disabled. There is no contributor agreement
because there is no contribution process. See `LICENSE.md`: reading the source is the only use
contemplated.

While this repository is hosted publicly on GitHub, GitHub users have the rights GitHub's Terms
of Service confer in respect of public repository content, including viewing and forking. Those
are the only rights granted, and none of them permit use, modification, or redistribution
outside GitHub's Service. See `LICENSE.md`.

The single exception to "no correspondence" is a security report. See `SECURITY.md`.

## Repository rules

This repository is public from its first commit, and its history is public along with it.
Nothing can be added and later removed — a deleted file stays in the history, and a rewritten
history does not reach anyone who already cloned. So these rules apply to every file, every
comment, every commit message and every test fixture, from the first commit onward:

- **No internal material.** No internal documents, planning or design records, review chains,
  handovers, or evidence of any kind. This repository carries source and the documentation a
  reader of that source needs — nothing about how it came to be written.
- **No deployment configuration values.** No account identifiers, stack names, bucket names,
  distribution identifiers, role names, or any other environment-specific value. Ever, in any
  file. Infrastructure definitions may live here; the values they are deployed with do not.
- **No secrets.** None exist here by construction, and nothing may introduce one. A viewer that
  needed a secret to do its job would be the wrong design, not a key-management problem.
- **No third-party assets.** Fonts, scripts, styles and images are first-party and stay that
  way. Nothing under `site/` may reference anything outside `site/`.
- **No attribution to tools in the history.** A commit message says what changed. It does not
  credit the change, or itself, to whatever was used to write it: no co-author trailer naming a
  tool rather than a person, no "generated with" or "generated by" line, and no product or vendor
  name anywhere — not in the message, and not in the name or address a commit is recorded under.

## What the checks defend against

`npm run check` is a gate against **silent** defeats of shipped behaviour. A one-token change to a
module under `site/`, a comparator relaxed, a flag flipped, a control neutered — each of those
leaves the test suite intact, and an intact suite refuses them. That is the whole of what these
checks are built to catch, and the pins, floors, name lists and required-test identities all exist
to close the routes by which such a change could pass unnoticed.

They do **not** defend against an author who overtly edits the test suite itself. Skipping a
required test, renaming one, changing a fixture's key, emptying a required list — every one of
those is a change to a public, reviewed file, and every one of them shows in the diff. There is no
check inside a repository that can stop its own tests being rewritten, and building one is an
infinite regress: whatever guards the suite is itself a file in the suite. So that boundary is
drawn here deliberately rather than chased.

Required-test identities close the case where the two overlapped — where skipping a pin also hid a
hole in shipped code, and the skip itself was the quiet part. They close it on one condition, and
the condition is a line of the runner rather than an argument: a test that did not run must not be
recorded as one. A skipped test reaches the runner as a pass carrying a flag, so what keeps it out
of the executed set is where the recording call sits in the handler that reads that flag — moved
one line out of the guard it sits in, a skipped test satisfied its own required title and the whole
gate went green with a pin skipped out. That line is now held from outside the runner:
`scripts/run-node-tests-selftest.mjs` spawns the runner against fixture trees of nothing but
skipped and nothing but pending tests, names required titles on its command line, and requires
every one of them to come back reported as not executed.

Beyond that, a test-suite edit that defeats a pin is a residual bounded by code review of this
repository, not by anything the gate can do.

### A green local run is not proof that the gate ran

Every check is reached through one npm script, and every step of that script is a string in
`package.json`. The two runners that read `package.json` back and compare it against its pins are
themselves reached only through those step names — so replacing all of them with a command that
does nothing leaves `npm run check` exiting 0 having run none of it, and nothing left to notice.
That is not a bar with a height: it holds for three of the five steps, for four, and for all five,
with the chain itself left byte-identical.

CI does not share that blind spot. `.github/workflows/ci.yml` runs the chain by name and also runs
a runner by its path, in a step of its own. Reaching the runner by path does not consult the step
names at all, and that runner reads the whole manifest — so one such step reports every substituted
step, and a manifest silenced in this way fails in CI whatever it does locally.

What remains is that `ci.yml` is itself a file, and it can be edited. Deleting either step, or the
workflow altogether, is caught: `check:self` reads that file and requires both steps to be in it.
This section used to say that what survived from there on was configuration held elsewhere — a
workflow disabled in the project's settings, a result nothing is required to wait for. That was
wrong, and wrong in the direction that matters: edits confined to files in this repository, passing
every check in it, survive too. Each of those is still a change to a public file in a public
repository, and the diff is the reviewable act — that is what the boundary rests on, rather than a
check. What was false was only the claim that the surviving edits were held somewhere else.

### What a green run does and does not assure

The honest boundary is a trust base rather than a list. The subject of this gate is shipped code —
what is served from `site/`. `package.json`, `.github/**`, `scripts/**` and `test/**` are the gate:
they are the instrument, not the specimen, and they are trusted rather than defended against. What
a green run assures is exactly this and no more: with those files unchanged, a change confined to
shipped code that violates an explicit confidentiality, refusal, validation or output-fidelity
requirement fails. The result is therefore meaningful only when the gate files under review are
unchanged and CI actually ran. Anyone able to modify the gate, the CI settings, the publishing path
or the owner's credentials bypasses this assurance entirely; preventing that needs a trust root
outside this repository, which this repository cannot provide.

The following are named rather than chased. Each sits inside the trust base, and closing any one of
them would not change the sentence above:

- A workflow whose run steps are spelled as environment keys rather than as `run:`.
- A `NODE_OPTIONS` set on a single step.
- A runner conditioned on the path it was invoked by.
- A test declared with no callback, which the runner records as pending rather than as failing.
- The indentation reader in `scripts/check-attribution-selftest.mjs`. Its block level is fixed by
  the first line deeper than the header, so a step that writes a nested block before its own keys
  has that nested block's keys read as the step's own, and its `uses:` line read as nothing at all.
  The push-trigger and checkout-depth readings rest on that same function. The action pin does not:
  that reading is a scan for a line prefix and never calls it.
- The whitespace and the line breaks that same reader does not see. It splits the workflow on a line
  feed or on a carriage-return-and-line-feed pair, and it measures indentation as however much
  `trimStart` removes — so a bare carriage return is not a line break to it, and a non-breaking
  space is indentation to it while YAML's indentation is spaces and nothing else. A trigger block
  indented with the second is read here as the keys it looks like and is not those keys to a parser,
  which leaves the workflow with no trigger at all; a line break written as the first is a break a
  parser takes and this reader does not, which is somewhere a filter can sit. Both spellings leave
  every line-level pin in this repository passing.
- That YAML 1.1 resolves `on`, `yes` and `true` to one key. A second top-level `true:` block is the
  same key as `on:` to a parser, while the count that requires exactly one top-level `on` is looking
  for the word — so the trigger can be replaced with the word `push` left where every reader looks.

One class of residual is closed by an argument rather than by cases, and it is worth saying which
and why. The output-fidelity requirement quantifies over every value a share can carry; the corpus
quantifies over the values it does carry. A predicate chosen after reading a finite corpus can
always be made true only outside that corpus, so for any list of cases there is a transform gated on
something none of them happens to be — an interval, a container count, a character, a flag. Cases
are still added when one is found, and adding them is not progress towards closing the class. What
closes it is that argument together with the reviewable diff: a rewrite of what a validator returns
is a change to a public file in a public repository. The alternative that would close it by
construction is a generator drawn from the schema rather than a corpus about a validator, and it is
named here as deliberately not taken. The instances left open by design are transforms gated on
container counts or on windows the corpus skips, expiry intervals beyond the covered band,
identifier substitutions beyond the covered alphabet, and predicates on any axis every fixture holds
constant. No longer list changes the paragraph above it; a longer list moves one named instance from
open to closed, one value at a time.

Two runtime controls are named in the code as arriving with the deploy configuration rather than
here: CSP `connect-src` for network egress, and CSP `style-src`/`img-src` for what a stylesheet
fetches. The build-time checks assert the same requirements at the earliest point they can be
asserted; they are not a substitute for the runtime ones.

## Working copy setup

One line, in a clone of this repository:

```
git config core.hooksPath .githooks
```

That points git at `.githooks/`, whose `commit-msg` hook refuses a message breaking the last
rule above. It is local configuration rather than a commit, so it does not travel with a clone
and cannot be relied on — which is why `.github/workflows/ci.yml` reads the whole history for
the same thing. That is what covers a hook nobody wired up, a hook that was skipped, and a
commit made somewhere else entirely.
